# Requirements: BKK CivicConnect AI

อ้างอิง: `intent-statement.md` (Intent Capture), `scope-document.md` (Scope Definition), `team-practices.md` (Practices Discovery) และคำตอบใน `requirements-analysis-questions.md` ([Q<n>] คือหมายเลขคำถามในไฟล์นั้น) ความต้องการที่มาจากเอกสาร PRD (`docs/requirements.md`) ระบุเป็น [PRD] ความต้องการที่มาจากขั้นตอน Rough Mockups ระบุเป็น [RM-Q<n>] และจาก Feasibility ระบุเป็น [FE-Q<n>]

## Intent analysis

ระบบต้องให้ประชาชนชาวกรุงเทพฯ แจ้งปัญหาเมืองและสอบถามข้อมูลราชการผ่านการโทรเข้าศูนย์ 1555 โดยไม่ต้องรอสายนาน ระบบแปลงคำพูดเป็น Ticket ที่ติดตามสถานะได้ และช่วยเจ้าหน้าที่ด้วยหน้าจอสรุปเมื่อสายถูกโอนมา [intent-statement.md] [PRD] เป้าหมายคือต้นแบบที่สาธิตสดได้วันที่ 30 พฤศจิกายน 2569 [intent-statement.md]

ลำดับความสำคัญแบบ MoSCoW ใช้ตาม `scope-document.md` ดังนี้ ต้องมี (Must): FR1, FR2, FR3, FR4, FR5 (FR5 ตัดได้เป็นอันดับที่ 2) มีก็ดี (Could): FR6, FR8 และ FR2.6 (ปุ่มส่งต่อสำนักงานเขต) ซึ่งตัดได้เมื่อเวลาไม่พอ

## Functional requirements

### FR1 รับสายผ่าน Genesys Cloud (Must, ทำก่อนทุกอย่าง)

- **FR1.1** ระบบรับสายเสียงที่โทรเข้า Genesys Cloud จริง (org `ark-insights`) [scope-document.md] [FE-Q1] [PRD]
  - เกณฑ์ผ่าน: เมื่อโทรเข้าเบอร์ทดสอบ ระบบรับสายและเริ่มโต้ตอบได้
- **FR1.2** ระบบแยกประเภทสายเป็น "แจ้งปัญหาเมือง" หรือ "ถามข้อมูลบริการ" [PRD]
  - เกณฑ์ผ่าน: ตัวอย่างเช่นประโยค "ท่อระบายน้ำแตก น้ำท่วมซอยสุขุมวิท 50" ถูกจัดเป็นแจ้งปัญหา

### FR2 รับแจ้งปัญหาและสร้าง Ticket (Must)

- **FR2.1** ระบบสกัดประเภทปัญหา สถานที่ และระดับความเร่งด่วนจากคำพูด [Q2] [Q3] [Q4]
  - ประเภทที่รองรับ: ท่อระบายน้ำและน้ำท่วม, ทางเท้าชำรุด, และ "อื่นๆ" ที่เจ้าหน้าที่ตรวจต่อ [Q3]
  - ระดับความเร่งด่วนมี 3 ระดับ (High, Medium, Low) และ AI เป็นผู้ตัดสินจากคำพูด [Q4]
  - เกณฑ์ผ่าน: คำพูด "ท่อแตก น้ำท่วมซอยสุขุมวิท 50 อันตรายมาก" ได้ประเภทท่อระบายน้ำและน้ำท่วม, ซอยสุขุมวิท 50 เขตคลองเตย, ระดับ High [PRD]
- **FR2.2** ถ้าสถานที่ไม่ชัด ระบบถามกลับ 1 ครั้งเพื่อยืนยันซอยและเขต [Q5]
- **FR2.3** ระบบสร้าง Ticket และออก Ticket ID ในรูปแบบ `BKK-2026-XXXX` [PRD]
- **FR2.4** Ticket เก็บ ประเภทปัญหา สถานที่ (ซอยและเขต) ระดับความเร่งด่วน ข้อความสรุปที่ AI เขียน เวลาที่แจ้ง สถานะ และหน่วยงานรับผิดชอบ [Q2]
- **FR2.5** ระบบไม่เก็บข้อความที่ประชาชนพูดตามที่ถอดได้ใน Ticket [Q2]
- **FR2.6** ปุ่มส่ง Ticket ต่อให้สำนักงานเขต เป็นส่วนมีก็ดี (Could) [scope-document.md]

### FR3 แจ้ง Ticket ID ให้ผู้แจ้งทาง SMS (Must)

- **FR3.1** เมื่อสร้าง Ticket สำเร็จ ระบบส่ง SMS แจ้ง Ticket ID ไปยังเบอร์ที่โทรเข้า (Caller ID) จาก Genesys [RM-Q5] [Q6]
- **FR3.2** ระบบไม่เก็บเบอร์โทรไว้ใน Ticket หลังส่ง SMS [Q6]
- **FR3.3** ถ้าไม่มี Caller ID (เบอร์ถูกซ่อน) Ticket ยังต้องถูกสร้างและ SMS ถูกข้าม [assumption]

### FR4 ดูและติดตามสถานะ Ticket (Must)

- **FR4.1** เจ้าหน้าที่ดูรายการ Ticket กรองตามสถานะ และเปิดดูรายละเอียดได้ [RM-Q1] [RM-Q2]
- **FR4.2** ประชาชนตรวจสอบสถานะด้วย Ticket ID ผ่านหน้าเว็บ ใช้บนมือถือได้ [RM-Q1] [RM-Q2] [RM-Q6]
  - เกณฑ์ผ่าน: Ticket ID ที่ถูกต้องแสดงสถานะปัจจุบัน ส่วน Ticket ID ที่ไม่พบแสดงข้อความว่าไม่พบและให้กรอกใหม่ [assumption]
- **FR4.3** สถานะมี 3 ค่า คือ รับเรื่องแล้ว, กำลังดำเนินการ, แก้ไขเสร็จ [RM-Q9]
- **FR4.4** เจ้าหน้าที่เปลี่ยนสถานะ Ticket เองในหน้ารายการ Ticket [Q10]

### FR5 ตอบคำถามข้อมูลระเบียบ กทม. (Must, ตัดได้เป็นอันดับที่ 2)

- **FR5.1** ระบบตอบคำถามเฉพาะที่อยู่ในชุดข้อมูลตัวอย่าง (Mock Civic Dataset) [Q9] [intent-statement.md]
- **FR5.2** ถ้าคำถามอยู่นอกชุดข้อมูล ระบบบอกตรงๆ ว่าไม่มีข้อมูล และเสนอโอนสายหาเจ้าหน้าที่ [Q9]
- **FR5.3** หัวข้อที่ชุดข้อมูลต้องครอบคลุมยังไม่ได้กำหนด [Q8] (ดู Open questions)

### FR6 AI Copilot บนหน้าจอเจ้าหน้าที่ (Could)

- **FR6.1** Widget แสดงสรุป 3 ข้อ และข้อมูล Ticket ที่ส่วนบนสุดเมื่อสายโอนเข้า [RM-Q3] [RM-Q4]
- **FR6.2** บทสนทนาสดภาษาไทยเปิดดูเพิ่มได้ [RM-Q3]
- **FR6.3** ใช้ใน Genesys Agent Workspace บนคอมพิวเตอร์ [RM-Q1] [RM-Q6]

### FR7 ทางออกเมื่อระบบเข้าใจคำพูดไม่ได้ (Must)

- **FR7.1** ถ้าระบบเข้าใจคำพูดไม่ได้ ระบบถามซ้ำสูงสุด 2 ครั้ง แล้วโอนสายหาเจ้าหน้าที่ [Q7]
- **FR7.2** ถ้าผลลัพธ์ของ AI ไม่อยู่ในรูปแบบที่ตรวจสอบได้ ให้ถือว่าเข้าใจคำพูดไม่ได้ และใช้ FR7.1 [assumption]

### FR8 แจ้งเตือนผ่าน LINE OA (Could)

- **FR8.1** การแจ้งเตือนผู้แจ้งผ่าน LINE OA มีได้แต่ไม่จำเป็น [RM-Q5]

## Non-functional requirements

- **NFR1 ความเร็วในการตอบ:** AI ตอบคำถามระเบียบ กทม. ภายใน 2 วินาที นับจากประชาชนพูดจบประโยคจนระบบเริ่มตอบ [Q1]
- **NFR2 การเข้าถึง:** ทุกหน้าจอทำตามพื้นฐาน WCAG 2.1 AA และสถานะต้องมีข้อความกำกับ ไม่ใช้สีอย่างเดียว [RM-Q7]
- **NFR3 ข้อมูลส่วนบุคคล:** ใช้เฉพาะข้อมูลและเสียงสมมติของทีมในการสาธิต และไม่เก็บเบอร์โทรไว้หลังส่ง SMS [FE-Q3] [Q6]
- **NFR4 คุณภาพโค้ดและการทดสอบ:** เขียนการทดสอบก่อนโค้ดแบบ TDD และครอบคลุมบรรทัดโค้ดไม่ต่ำกว่า 80% [team-practices.md]
- **NFR5 การรันระบบ:** ระบบสาธิตรันบนเครื่องของทีม โดยโมเดลภาษาและการแปลงเสียงรันภายในเครื่องหรือระบบของทีมเอง และไม่ใช้ AWS [FE-Q9] [FE-Q8] [team-practices.md]
- **NFR6 ภาษา:** ระบบรับและโต้ตอบภาษาไทยธรรมชาติ [PRD]

## Constraints

- เวลาพัฒนา 1 วัน ส่งผลงานภายใน 14:30–15:00 น. วันที่ 30 พฤศจิกายน 2569 และไม่มีงบเพิ่ม [FE-Q5]
- ระบบภายนอกที่เชื่อมต่อได้มีเพียง Genesys Cloud CX (org `ark-insights`) [FE-Q1]
- โฟลเดอร์ทำงานยังไม่ใช่ git repository ต้องรัน `git init` ก่อนเริ่มเขียนโค้ด [team-practices.md]

## Assumptions

- ถ้าไม่มี Caller ID ระบบข้าม SMS แต่ยังสร้าง Ticket (FR3.3) เหตุผล: Ticket สำคัญกว่าการแจ้งเตือน [assumption]
- ผลลัพธ์ AI ที่ผิดรูปแบบถือเป็นเข้าใจคำพูดไม่ได้ (FR7.2) เหตุผล: กันไม่ให้ Ticket ที่ข้อมูลเสียถูกสร้าง [assumption]
- หนึ่งสายสร้าง Ticket ได้ไม่เกินหนึ่งใบ และสายที่โทรซ้ำถือเป็นเรื่องใหม่ ไม่ตรวจซ้ำ เหตุผล: ไม่มีข้อกำหนดเรื่องการตรวจ Ticket ซ้ำในขอบเขตเวอร์ชันแรก [assumption]
- Ticket ID ที่ไม่พบแสดงข้อความว่าไม่พบ (FR4.2) เหตุผล: เส้นทางเมื่อผิดพลาดต้องกำหนด [assumption]

## Out of scope

- ช่องทางข้อความรับเรื่อง (Web Chat / LINE), การ Fine-tune โมเดลใหม่, ฐานข้อมูลระเบียบครบ 50 เขต และการเชื่อมระบบรับเรื่องจริงของ กทม. [intent-statement.md]
- ข้อบังคับด้านข้อมูลส่วนบุคคลของข้อมูลจริง เพราะใช้เฉพาะข้อมูลสมมติ [FE-Q3]

## Open questions

- **หัวข้อของการถามข้อมูลระเบียบ กทม. (FR5.3):** ยังไม่กำหนด จึงตรวจรับ FR5 ยากจนกว่าจะระบุหัวข้อที่ชุดข้อมูลตัวอย่างต้องครอบคลุม [Q8]
- **ประชาชนจะได้ Ticket ID อย่างไรถ้า SMS ส่งไม่ถึง:** ยังไม่ได้กำหนด [RM-Q5]
- **การป้องกันการเดา Ticket ID:** Ticket ID เรียงลำดับเดาได้อาจให้คนอื่นดูสถานะเรื่องของผู้อื่นได้ ยังไม่ได้ตัดสิน
- **เสียงตอบกลับอัตโนมัติ (ระบบพูดตอบประชาชน):** PRD กล่าวถึง แต่ `scope-document.md` ยังไม่ได้จัดว่าอยู่ในขอบเขตหรือไม่ จึงไม่ได้เขียนเป็นความต้องการ
- **ความขัดแย้งกับ `scope-document.md`:** เอกสารขอบเขตจัด SMS เป็นส่วนมีก็ดีและตัดก่อนเป็นอันดับแรก แต่ความต้องการนี้จัด FR3 เป็น Must ตามคำตอบล่าสุดในขั้นตอน Rough Mockups [RM-Q5] ต้องปรับเอกสารขอบเขตให้ตรงกัน
