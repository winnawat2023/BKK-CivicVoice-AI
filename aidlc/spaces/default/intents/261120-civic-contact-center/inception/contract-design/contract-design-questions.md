# Contract Design — คำถามเพื่อกำหนดสัญญาระหว่าง Unit

> อ้างอิงจาก `unit-of-work.md`, `unit-of-work-dependency.md` (Units Generation), `components.md` (Domain Design) และ `requirements.md` สัญญาคือข้อตกลงข้ามขอบเขต ว่าข้อมูลอะไรผ่านไป รูปแบบใด และเกิดอะไรเมื่อล้มเหลว ขอบเขตที่ต้องมีสัญญามี 7 จุด ได้แก่ (1) TicketService, (2) Conversation ถึง KnowledgeAnswer, (3) Conversation ถึง Notification, (4) การผลักข้อมูลจาก Conversation ไป AgentWidget, (5) CallChannel กับ Genesys Cloud (ภายนอก), (6) จุดต่อขยายของ Conversation สำหรับ U2, U3, U6 (ข้อสังเกต R-01 จาก Units Generation) และ (7) การค้นสถานะ Ticket สำหรับประชาชน (ข้อสังเกต R-01 จาก Domain Design)

## Q1. [สถาปนิก] ขอบเขตแต่ละจุดสื่อสารกันด้วยวิธีใด

เหตุผลที่ถาม: ส่วนหลังบ้านทั้งหมดติดตั้งเป็นชิ้นเดียว [Q4 ของ Units Generation] จึงไม่จำเป็นต้องเรียกกันผ่านเครือข่าย แต่หน้าเว็บและ Genesys อยู่นอกชิ้นนั้น

- A. ภายในชิ้นหลังบ้าน เรียกกันผ่านอินเทอร์เฟซในโปรแกรม (in-process) ส่วนหน้าเว็บ (TicketWeb, AgentWidget) กับ Genesys ใช้ HTTP แบบ JSON และการผลักข้อมูลไป Widget ใช้การเชื่อมต่อแบบเรียลไทม์ตาม ADR-004
- B. ทุกขอบเขตใช้ HTTP แบบ JSON รวมถึงภายในหลังบ้าน
- C. Not yet defined
- X. Other (please specify)

[Answer]: A

## Q2. [เจ้าของผลิตภัณฑ์] การค้นสถานะด้วย Ticket ID จากหน้าสาธารณะควรคืนข้อมูลอะไร

เหตุผลที่ถาม: Ticket ID เดาได้ (ยอมรับความเสี่ยงสำหรับการสาธิต) จึงควรจำกัดข้อมูลที่คนทั่วไปเห็น ขณะที่รายการและรายละเอียดเต็มสงวนให้เจ้าหน้าที่

- A. คืนเฉพาะสถานะปัจจุบัน (รับเรื่องแล้ว, กำลังดำเนินการ, แก้ไขเสร็จ) ไม่คืนประเภทปัญหา สถานที่ หรือข้อความสรุป
- B. คืนสถานะ ประเภทปัญหา และเขต
- C. Not yet defined
- X. Other (please specify)

[Answer]: B

## Q3. [สถาปนิก] ใครเป็นเจ้าของสัญญาแต่ละฉบับ

เหตุผลที่ถาม: สัญญาที่ไม่มีเจ้าของจะถูกแก้ตามใจและทำให้ Unit ที่สร้างขนานกันชนกัน

- A. Unit ที่ให้บริการ (provider) เป็นเจ้าของ เช่น U1 เป็นเจ้าของสัญญาของ TicketService และการเปลี่ยนที่ทำให้ผู้ใช้เสียต้องตกลงกับ Unit ที่ใช้
- B. Unit ที่ใช้ (consumer) กำหนดสิ่งที่ต้องการ แล้ว Unit ที่ให้บริการทำตาม
- C. Not yet defined
- X. Other (please specify)

[Answer]: A

## Q4. [เจ้าของผลิตภัณฑ์] ถ้าสร้าง Ticket ไม่สำเร็จ (เช่น ที่เก็บ Ticket ใช้ไม่ได้) ประชาชนที่รอสายอยู่ควรเจออะไร

เหตุผลที่ถาม: เป็นช่องว่างที่ผู้ตรวจพบใน User Stories (ไม่มีเกณฑ์สำหรับสร้าง Ticket ไม่สำเร็จ) และกระทบสัญญาระหว่าง Conversation กับ TicketService

- A. แจ้งว่าระบบขัดข้องและโอนสายหาเจ้าหน้าที่
- B. แจ้งว่าระบบขัดข้องและให้โทรใหม่ แล้ววางสาย
- C. Not yet defined
- X. Other (please specify)

[Answer]: A

## Q5. [สถาปนิก] เมื่อมีคนต้องการเปลี่ยนสัญญา จะจัดการอย่างไร

เหตุผลที่ถาม: ทีมมีเวลาวันเดียวและสร้างหลาย Unit พร้อมกัน การเปลี่ยนสัญญากลางทางทำให้ Unit ที่สร้างไปแล้วพัง

- A. ไม่มีเวอร์ชัน (เวลาไม่พอ) แต่การเพิ่มช่องข้อมูลใหม่ทำได้เสมอโดยผู้ใช้ต้องไม่สนใจช่องที่ไม่รู้จัก ส่วนการแก้หรือลบช่องเดิมต้องตกลงกับเจ้าของและ Unit ที่ใช้ก่อน
- B. กำหนดเลขเวอร์ชันให้ทุกสัญญาตั้งแต่ต้น (เช่น v1) เพื่อรองรับการเปลี่ยนภายหลัง
- C. Not yet defined

## Q6. [สถาปนิก] เมื่อบริการภายนอกช้าหรือล้มเหลว (Genesys, ช่องทางส่ง SMS, โมเดลภาษา, การแปลงเสียง) ควรทำอย่างไร

## Q7. [สถาปนิก] จะกันไม่ให้ Unit ที่สร้างขนานกันแก้ไฟล์เดียวกันได้อย่างไร

เหตุผลที่ถาม: ผู้ตรวจพบว่า U2, U3 และ U6 ต่างขยาย Conversation และ U4 กับ U5 ต่างขยาย TicketService ตัวเดียวกัน (ข้อสังเกต R-01 จาก Units Generation) ซึ่งเสี่ยงชนกันตอนรวมงาน

- A. U1 วางจุดต่อขยายไว้ก่อน คือ Conversation มีตัวจัดการแยกตามเหตุการณ์ (แจ้งปัญหา ถามข้อมูล ไม่เข้าใจ) ที่แต่ละ Unit เพิ่มไฟล์ของตัวเอง และ TicketService แยกโมดูลอ่านสถานะ รายการและเปลี่ยนสถานะ และสร้าง ออกจากกัน แต่ละ Unit แก้เฉพาะโมดูลของตน
- B. ไม่วางจุดต่อขยาย ให้แต่ละ Unit แก้ไฟล์ร่วมกันและแก้ความขัดแย้งตอนรวมงาน
- C. Not yet defined
- X. Other (please specify)
