# Architecture Decision Records: BKK CivicConnect AI

อ้างอิง: `requirements.md` (Requirements Analysis), `stories.md` (User Stories), `team-practices.md` (Practices Discovery), `components.md` และคำตอบใน `domain-design-questions.md` ([Q<n>] คือหมายเลขคำถามในไฟล์นั้น) แต่ละ ADR ระบุผลด้านความปลอดภัยและข้อกำหนดตามกฎของเฟส Inception ที่ต้องพิจารณาทุกการตัดสินใจสำคัญ

## ADR-001: แบ่งระบบตามความรับผิดชอบเป็นส่วนประกอบเล็กที่ทดสอบแยกได้

- **Context:** ทีม 3–4 คนมีเวลาวันเดียว ใช้ TDD และขอบเขตมีส่วนที่ตัดได้หลายชิ้น (ถามข้อมูลระเบียบ, SMS, AI Copilot) [team-practices.md] [scope-document.md]
- **Decision:** แบ่งตามความรับผิดชอบ (ตัวเลือก A ของ Q1) [Q1] เมื่อรวมกับ ADR-005 ได้ 7 ส่วน: CallChannel, Conversation, KnowledgeAnswer, TicketService, Notification, AgentWidget และ TicketWeb
- **Consequences:** ข้อดีคือแต่ละส่วนทดสอบแยกได้ ทีมแบ่งงานขนานกันได้ และตัดส่วนมีก็ดีออกได้โดยไม่กระทบส่วนหลัก ข้อเสียคือมีจุดเชื่อมต่อมากขึ้นซึ่งต้องกำหนดสัญญาในขั้นตอน Contract Design
- **Alternatives Rejected:** แบ่งหยาบ 3 ส่วน (VoiceFlow, TicketService, Web) เพราะ VoiceFlow ใหญ่ ตัดส่วนที่ตัดได้ยาก และทดสอบแยกยากกว่า [Q1]
- **ความปลอดภัยและข้อกำหนด:** การแยกส่วนทำให้ข้อมูลที่อ่อนไหว (เบอร์โทร) ผ่านเฉพาะ CallChannel, Conversation และ Notification ตาม ADR-007

## ADR-002: การสนทนาเป็นข้อมูลของส่วน Conversation และ Ticket อ้างอิงถึงมัน

- **Context:** Widget แสดงสรุป 3 ข้อของสาย แต่สายที่ถามข้อมูลแล้วโอนมาอาจไม่มี Ticket ขณะที่ Ticket เก็บข้อความสรุปที่ AI เขียน (FR2.4) อีกค่าหนึ่ง [Q2] [requirements.md]
- **Decision:** แยกข้อมูล Conversation ให้ส่วน Conversation เป็นเจ้าของ เก็บสรุป 3 ข้อและสถานะสาย ส่วน Ticket (ของ TicketService) อ้างถึง conversationId ทิศทางเดียว [Q2]
- **Consequences:** ข้อดีคือทุกสายมีสรุปได้ ไม่ว่ามี Ticket หรือไม่ และข้อมูลแต่ละชิ้นมีเจ้าของเดียว ข้อเสียคือการค้นหา Ticket ของสายหนึ่งต้องค้นย้อนกลับ และมีข้อมูลสรุปสองค่า (สรุป 3 ข้อ และข้อความสรุปใน Ticket) ที่ต้องรักษาให้สอดคล้อง
- **Alternatives Rejected:** ใส่สรุป 3 ข้อไว้ใน Ticket ทั้งหมด เพราะสายที่ไม่มี Ticket จะไม่มีสรุปให้ Widget [Q2]
- **ความปลอดภัยและข้อกำหนด:** ไม่มี Ticket ที่เก็บข้อความที่พูดหรือเบอร์โทร ตาม FR2.5 และ FR3.2

## ADR-003: เก็บสรุป 3 ข้อไว้หลังสายจบ ไม่เก็บบทสนทนา

- **Context:** เจ้าหน้าที่ต้องดูสรุปย้อนหลังได้ ขณะที่ FR2.5 ห้ามเก็บข้อความที่พูดใน Ticket [Q3] [requirements.md]
- **Decision:** เก็บสรุป 3 ข้อไว้ใน Conversation หลังสายจบ ไม่เก็บบทสนทนา [Q3]
- **Consequences:** ข้อดีคือเจ้าหน้าที่ดูย้อนหลังได้ ข้อเสียคือสรุปอาจมีสถานที่หรือรายละเอียดส่วนบุคคลหลงเหลือ และ FR2.5 พูดถึง Ticket เท่านั้น ยังไม่ครอบคลุมการสนทนา จึงควรเพิ่มข้อกำหนดการเก็บและลบข้อมูลสรุปในขั้นตอนถัดไป
- **Alternatives Rejected:** เก็บเฉพาะระหว่างสายและลบเมื่อสายจบ ไม่ได้เลือก เพราะเจ้าหน้าที่ดูย้อนหลังไม่ได้ [Q3]
- **ความปลอดภัยและข้อกำหนด:** ตอนนี้ใช้เฉพาะข้อมูลสมมติ [FE-Q3 ของ Feasibility] ถ้านำไปใช้กับข้อมูลจริงต้องกำหนดระยะเวลาเก็บและสิทธิ์การเข้าถึงก่อน [assumption]

## ADR-004: ผลักบทสนทนาสดไปยัง Widget (push)

- **Context:** PRD ระบุการเชื่อมต่อแบบเรียลไทม์ และ AI Copilot แสดงบทสนทนาสด [Q4] [PRD]
- **Decision:** Conversation ผลักข้อความไปยัง AgentWidget ทันทีที่มีข้อความใหม่ ความสัมพันธ์เป็นแบบเหตุการณ์ (event) [Q4]
- **Consequences:** ข้อดีคือหน่วงเวลาน้อยและตรงตาม PRD ข้อเสียคือต้องจัดการการเชื่อมต่อที่หลุดและเชื่อมใหม่ ซึ่งซับซ้อนกว่าการดึงเป็นระยะ และ AgentWidget เป็นส่วนมีก็ดี
- **Alternatives Rejected:** ให้ Widget ดึงข้อมูลเป็นระยะ (poll) เพราะล่าช้ากว่าและไม่ตรงตาม PRD [Q4]
- **ความปลอดภัยและข้อกำหนด:** ต้องให้เฉพาะ Widget ของสายนั้นรับข้อความของสายนั้น ไม่ปะปนกับสายอื่น (กำหนดรายละเอียดใน Contract Design) [assumption]

## ADR-005: แยก AgentWidget ออกจาก TicketWeb

- **Context:** Widget ต้องฝังใน Genesys Agent Workspace ส่วนรายการ Ticket และหน้าตรวจสอบสถานะเป็นหน้าเว็บที่ผู้ใช้คนละกลุ่ม [Q5]
- **Decision:** แยกเป็นสองส่วนประกอบ AgentWidget และ TicketWeb [Q5] ซึ่งทำให้ส่วน "เว็บ" ของ ADR-001 แยกเป็นสองส่วน
- **Consequences:** ข้อดีคือ AgentWidget ตัดได้โดยไม่กระทบ TicketWeb และรูปแบบการติดตั้งต่างกันได้ ข้อเสียคือส่วนประกอบหน้าจอที่ใช้ร่วมกันต้องแชร์ข้ามสองส่วน
- **Alternatives Rejected:** แอปเว็บเดียวมี 3 มุมมอง เพราะผูก Widget ที่ตัดได้เข้ากับหน้าที่ต้องมี [Q5]
- **ความปลอดภัยและข้อกำหนด:** หน้าตรวจสอบสถานะของประชาชนเปิดสาธารณะ จึงต้องแยกสิทธิ์จากหน้ารายการของเจ้าหน้าที่ ซึ่งขัดกับสมมติฐานเรื่องการเดา Ticket ID ที่ยอมรับไว้เฉพาะการสาธิต [assumption]

## ADR-006: ไม่มีทางป้อนสายจำลองเป็นส่วนหนึ่งของระบบ

- **Context:** ทีมใช้ TDD แต่ต้องมีแผนสำรองวันสาธิต (วิดีโอสำรองไม่เกิน 3 นาทีตามกติกาการแข่งขัน) [Q6] [competition-details]
- **Decision:** ทดสอบกับ Genesys จริงเท่านั้น ไม่มีทางป้อนสายจำลองเป็นส่วนหนึ่งของระบบ [Q6] การทดสอบหน่วยของแต่ละส่วนใช้ตัวแทนภายในการทดสอบได้ตามปกติ และ CallChannel ยังเป็นส่วนเดียวที่รู้จัก Genesys
- **Consequences:** ข้อดีคือระบบไม่มีส่วนที่ไม่ใช้ในการสาธิตจริง ข้อเสียคือการซ้อมและการทดสอบรวมต้องโทรจริงทุกครั้ง ถ้า Genesys หรือเครือข่ายหน้างานมีปัญหา จะทดสอบรวมและซ้อมไม่ได้ และแผนสำรองต้องอาศัยวิดีโอที่บันทึกจากการโทรจริงล่วงหน้า (ความเสี่ยง R3 ใน `raid-log.md`)
- **Alternatives Rejected:** มีทางป้อนสายจำลอง ไม่ได้เลือก [Q6] เหตุผลที่ผู้ตัดสินใจเลือกยังไม่ได้บันทึก [assumption]
- **ความปลอดภัยและข้อกำหนด:** ไม่เกี่ยวข้องโดยตรง เพราะไม่เพิ่มช่องทางรับข้อมูลใหม่

## ADR-007: เบอร์โทรไหลผ่านเส้นทางเดียวและไม่ถูกเก็บ

- **Context:** FR3 ต้องส่ง SMS ไปยังเบอร์ที่โทรเข้า แต่ FR3.2 ห้ามเก็บเบอร์ใน Ticket [requirements.md] [Q6 ของ Requirements Analysis]
- **Decision:** เบอร์ (Caller ID) ส่งจาก CallChannel ไป Conversation ไป Notification เท่านั้น และไม่ถูกเก็บในข้อมูลของส่วนใดหลังส่ง [assumption: เป็นผลของการออกแบบที่สืบจาก FR3.2]
- **Consequences:** ข้อดีคือลดข้อมูลส่วนบุคคลที่เก็บ ข้อเสียคือถ้า SMS ส่งไม่สำเร็จจะลองส่งใหม่ภายหลังไม่ได้ เพราะไม่มีเบอร์เหลือ ซึ่งสัมพันธ์กับคำถามค้างเรื่องผู้แจ้งไม่ได้ Ticket ID
- **Alternatives Rejected:** เก็บเบอร์ใน Ticket หรือ Conversation เพื่อส่งซ้ำ ไม่ได้เลือก เพราะขัดกับ FR3.2 ที่ยืนยันแล้ว
- **ความปลอดภัยและข้อกำหนด:** เบอร์โทรเป็นข้อมูลส่วนบุคคล จึงจำกัดเส้นทางและไม่เก็บ

## Assumptions & Open Questions

- ADR-001 ถึง ADR-006 มาจากคำตอบ Q1 ถึง Q6 ส่วน ADR-007 เป็นผลที่ผมสรุปจากข้อกำหนดที่ยืนยันแล้ว ยังไม่ได้ถามคุณโดยตรง [assumption]
- ข้อกำหนดการเก็บและลบสรุป 3 ข้อของสาย (ADR-003) ยังไม่มีใน `requirements.md`
- การแยกสิทธิ์ของหน้าตรวจสอบสถานะสาธารณะจากหน้ารายการเจ้าหน้าที่ (ADR-005) ยังไม่ได้ตัดสิน
- ผู้ตัดสินเลือกไม่ทำทางป้อนสายจำลองด้วยเหตุผลใด (ADR-006) ยังไม่ได้บันทึก
