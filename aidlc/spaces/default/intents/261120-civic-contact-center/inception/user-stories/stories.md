# User Stories: BKK CivicConnect AI

อ้างอิง: `requirements.md` (Requirements Analysis), `team-practices.md` (Practices Discovery) และคำตอบใน `user-stories-questions.md` ([Q<n>] คือหมายเลขคำถามในไฟล์นั้น) เรื่องราวจัดกลุ่มตาม role [Q2] แต่ละเรื่องมีขนาดเล็ก 1 เรื่องต่อ 1 ผลลัพธ์ที่ผู้ใช้เห็น [Q3] ตามหลัก INVEST ลำดับความสำคัญใช้ตาม `requirements.md` (Must Have, Could Have) ส่วนที่ยังไม่กำหนดบันทึกเป็นคำถามค้างของเรื่องนั้น ไม่เดาเกณฑ์ [Q4] ขอบเขต MVP จะตัดสินอย่างเป็นทางการใน Delivery Planning

ลำดับการทำงานตามวิธีทำงานของทีมคือทำชิ้นงานบางๆ ที่ครบทางก่อน (US1.1, US1.2, US1.4) แล้วจึงเพิ่มเรื่องอื่น [team-practices.md]

## กลุ่ม 1: ประชาชนผู้โทรเข้า (P1)

### US1.1 โทรเข้าและให้ระบบรับสาย (Must Have)

- **เรื่อง:** ในฐานะประชาชนผู้โทรเข้า ฉันต้องการให้ระบบรับสายและเข้าใจว่าฉันจะแจ้งปัญหาหรือถามข้อมูล เพื่อให้ได้รับบริการที่ตรงกับเรื่องของฉันโดยไม่ต้องรอเจ้าหน้าที่
- **ความต้องการที่เกี่ยวข้อง:** FR1.1, FR1.2, NFR6
- **เกณฑ์ผ่าน:**
  - **AC1.1.1** Given เบอร์ทดสอบของ Genesys Cloud ใช้งานได้ When ประชาชนโทรเข้า Then ระบบรับสายและเริ่มโต้ตอบเป็นภาษาไทย
  - **AC1.1.2** Given ระบบรับสายแล้ว When ประชาชนพูดว่า "ท่อระบายน้ำแตก น้ำท่วมซอยสุขุมวิท 50" Then ระบบจัดสายเป็น "แจ้งปัญหาเมือง"
  - **AC1.1.3** Given ระบบรับสายแล้ว When ประชาชนถามขั้นตอนทำบัตรประชาชน Then ระบบจัดสายเป็น "ถามข้อมูลบริการ"
- **ลำดับ:** ต้องเสร็จก่อนเรื่องอื่นทั้งหมดในกลุ่ม 1 [scope-document.md]
- **INVEST:** ทดสอบได้ด้วยการโทรจริงหรือจำลองเสียง และเล็กพอทำเสร็จในไม่กี่ชั่วโมง

### US1.2 แจ้งปัญหาและให้ระบบสร้าง Ticket (Must Have)

- **เรื่อง:** ในฐานะประชาชนผู้โทรเข้า ฉันต้องการพูดแจ้งปัญหาเมืองและให้ระบบสร้าง Ticket ที่มีข้อมูลครบ เพื่อให้เรื่องของฉันถูกส่งต่อโดยไม่ต้องให้เจ้าหน้าที่จดด้วยมือ
- **ความต้องการที่เกี่ยวข้อง:** FR2.1, FR2.3, FR2.4, FR2.5
- **เกณฑ์ผ่าน:**
  - **AC1.2.1** Given สายถูกจัดเป็นแจ้งปัญหา When ประชาชนพูดว่า "ท่อแตก น้ำท่วมซอยสุขุมวิท 50 อันตรายมาก" Then ระบบสร้าง Ticket ที่มีประเภท "ท่อระบายน้ำและน้ำท่วม" สถานที่ "ซอยสุขุมวิท 50 เขตคลองเตย" และความเร่งด่วน High
  - **AC1.2.2** Given ประชาชนแจ้งปัญหาที่ไม่อยู่ในสองประเภทหลัก When ระบบสร้าง Ticket Then ประเภทเป็น "อื่นๆ" เพื่อให้เจ้าหน้าที่ตรวจต่อ
  - **AC1.2.3** Given Ticket ถูกสร้างสำเร็จ When ดูข้อมูล Ticket Then มี Ticket ID รูปแบบ `BKK-2026-XXXX` ข้อความสรุปที่ AI เขียน เวลาที่แจ้ง สถานะ "รับเรื่องแล้ว" และหน่วยงานรับผิดชอบ
  - **AC1.2.4** Given Ticket ถูกสร้างสำเร็จ When ตรวจข้อมูลที่เก็บ Then ไม่มีข้อความที่ประชาชนพูดตามที่ถอดได้ใน Ticket
- **ลำดับ:** ต้องทำต่อจาก US1.1
- **INVEST:** ทดสอบได้ด้วยประโยคตัวอย่างจาก PRD
- **คำถามค้าง:** ความถูกต้องของการแปลงเสียงกับชื่อซอยและชื่อเขตยังไม่ได้ทดสอบ (ความเสี่ยง R2 ใน `raid-log.md`) [assumption]

### US1.3 ให้ระบบถามกลับเมื่อสถานที่ไม่ชัด (Must Have)

- **เรื่อง:** ในฐานะประชาชนผู้โทรเข้า ฉันต้องการให้ระบบถามกลับเมื่อฟังสถานที่ไม่ชัด เพื่อให้ Ticket ระบุซอยและเขตถูกต้อง
- **ความต้องการที่เกี่ยวข้อง:** FR2.2
- **เกณฑ์ผ่าน:**
  - **AC1.3.1** Given ประชาชนบอกสถานที่ที่ระบบระบุซอยหรือเขตไม่ได้ When ระบบประมวลผลคำพูด Then ระบบถามกลับเรื่องสถานที่ 1 ครั้ง
  - **AC1.3.2** Given ระบบถามกลับแล้ว 1 ครั้ง When ประชาชนตอบจนระบุซอยและเขตได้ Then ระบบสร้าง Ticket ด้วยสถานที่ที่ยืนยันแล้ว
- **ลำดับ:** ต้องทำต่อจาก US1.2
- **คำถามค้าง:** ถ้าถามกลับ 1 ครั้งแล้วยังไม่ชัด ผลที่ต้องการยังไม่ได้กำหนดใน `requirements.md` [assumption]

### US1.4 ได้รับ Ticket ID ทาง SMS (Must Have)

- **เรื่อง:** ในฐานะประชาชนผู้โทรเข้า ฉันต้องการได้รับ SMS แจ้ง Ticket ID เพื่อให้นำไปตรวจสอบสถานะเรื่องของฉันได้ภายหลัง
- **ความต้องการที่เกี่ยวข้อง:** FR3.1, FR3.2, FR3.3, NFR3
- **เกณฑ์ผ่าน:**
  - **AC1.4.1** Given Ticket ถูกสร้างและมี Caller ID When สร้าง Ticket สำเร็จ Then ระบบส่ง SMS แจ้ง Ticket ID ไปยังเบอร์ที่โทรเข้า
  - **AC1.4.2** Given ส่ง SMS เสร็จแล้ว When ตรวจข้อมูลใน Ticket Then ไม่มีเบอร์โทรเก็บอยู่ใน Ticket
  - **AC1.4.3** Given ไม่มี Caller ID (เบอร์ถูกซ่อน) When สร้าง Ticket สำเร็จ Then ระบบข้ามการส่ง SMS แต่ Ticket ยังถูกสร้าง
- **ลำดับ:** ต้องทำต่อจาก US1.2
- **คำถามค้าง:** ถ้า SMS ส่งไม่ถึง ประชาชนจะได้ Ticket ID อย่างไร และ SMS ส่งผ่านช่องทางใด ยังไม่ได้กำหนด (ตรงกับคำถามค้างใน `requirements.md`)
- **หมายเหตุ:** `scope-document.md` ยังจัด SMS เป็น Could ซึ่งขัดกับ FR3 ที่เป็น Must ใน `requirements.md` ต้องปรับให้ตรงกัน

### US1.5 ตรวจสอบสถานะ Ticket ด้วย Ticket ID (Must Have)

- **เรื่อง:** ในฐานะประชาชนผู้โทรเข้า ฉันต้องการกรอก Ticket ID บนมือถือเพื่อดูสถานะเรื่องของฉัน เพื่อให้รู้ว่าเรื่องคืบหน้าถึงไหน
- **ความต้องการที่เกี่ยวข้อง:** FR4.2, FR4.3, NFR2
- **เกณฑ์ผ่าน:**
  - **AC1.5.1** Given มี Ticket สถานะ "กำลังดำเนินการ" When ประชาชนกรอก Ticket ID ที่ถูกต้อง Then หน้าจอแสดงสถานะ "กำลังดำเนินการ" เป็นข้อความ ไม่ใช้สีอย่างเดียว
  - **AC1.5.2** Given ประชาชนกรอก Ticket ID ที่ไม่มีในระบบ When กดตรวจสอบ Then หน้าจอแจ้งว่าไม่พบและให้กรอกใหม่
  - **AC1.5.3** Given เปิดหน้าบนมือถือ When ใช้แป้นพิมพ์หรือโปรแกรมอ่านหน้าจอ Then ใช้งานช่องกรอกและปุ่มตรวจสอบได้ตามพื้นฐาน WCAG 2.1 AA
- **ลำดับ:** ต้องทำต่อจาก US1.2
- **คำถามค้าง:** การป้องกันการเดา Ticket ID ยังไม่ได้ตัดสิน (ตรงกับคำถามค้างใน `requirements.md`)

### US1.6 ถามข้อมูลระเบียบ กทม. (Must Have, ตัดได้เป็นอันดับที่ 2)

- **เรื่อง:** ในฐานะประชาชนผู้โทรเข้า ฉันต้องการถามขั้นตอนราชการและได้คำตอบทันที เพื่อไม่ต้องรอเจ้าหน้าที่
- **ความต้องการที่เกี่ยวข้อง:** FR5.1, FR5.2, NFR1
- **เกณฑ์ผ่าน (เฉพาะส่วนที่กำหนดแล้ว):**
  - **AC1.6.1** Given ชุดข้อมูลตัวอย่างมีคำตอบของคำถามนั้น When ประชาชนถามจบ Then ระบบเริ่มตอบภายใน 2 วินาที นับจากประชาชนพูดจบประโยค
  - **AC1.6.2** Given คำถามอยู่นอกชุดข้อมูลตัวอย่าง When ระบบประมวลผล Then ระบบบอกตรงๆ ว่าไม่มีข้อมูล และเสนอโอนสายหาเจ้าหน้าที่
- **ลำดับ:** ต้องทำต่อจาก US1.1 และตัดได้เป็นอันดับที่ 2 เมื่อเวลาไม่พอ [scope-document.md]
- **คำถามค้าง:** หัวข้อที่ชุดข้อมูลต้องครอบคลุมยังไม่กำหนด (FR5.3) จึงยังไม่มีเกณฑ์ผ่านที่ระบุคำถามตัวอย่างและคำตอบที่ถูกต้อง

### US1.7 โอนสายหาเจ้าหน้าที่เมื่อระบบฟังไม่เข้าใจ (Must Have)

- **เรื่อง:** ในฐานะประชาชนผู้โทรเข้า ฉันต้องการให้ระบบถามซ้ำและโอนสายหาเจ้าหน้าที่เมื่อฟังไม่เข้าใจ เพื่อไม่ให้ฉันติดค้างอยู่ในสาย
- **ความต้องการที่เกี่ยวข้อง:** FR7.1, FR7.2
- **เกณฑ์ผ่าน:**
  - **AC1.7.1** Given ระบบฟังคำพูดไม่เข้าใจ When ประชาชนพูดแล้วระบบยังไม่เข้าใจ Then ระบบถามซ้ำได้สูงสุด 2 ครั้ง
  - **AC1.7.2** Given ระบบถามซ้ำครบ 2 ครั้งแล้วยังไม่เข้าใจ When ครบจำนวนครั้ง Then ระบบโอนสายหาเจ้าหน้าที่
  - **AC1.7.3** Given ผลลัพธ์ของ AI ไม่อยู่ในรูปแบบที่ตรวจสอบได้ When ระบบประมวลผล Then ระบบถือว่าเข้าใจคำพูดไม่ได้และใช้ขั้นตอนถามซ้ำ
- **ลำดับ:** ต้องทำต่อจาก US1.1
- **คำถามค้าง:** นิยามของ "รูปแบบที่ตรวจสอบได้" ของผลลัพธ์ AI ยังไม่ชัด (เช่น ประเภทอยู่ในรายการที่รองรับ ระดับเป็น High, Medium หรือ Low) [assumption]

### US1.8 รับการแจ้งเตือนผ่าน LINE OA (Could Have)

- **เรื่อง:** ในฐานะประชาชนผู้โทรเข้า ฉันต้องการรับการแจ้งเตือนผ่าน LINE OA เพิ่มเติม เพื่อติดตามเรื่องได้สะดวก
- **ความต้องการที่เกี่ยวข้อง:** FR8.1
- **เกณฑ์ผ่าน:** ยังไม่กำหนด เพราะคำตอบระบุเพียงว่ามีได้แต่ไม่จำเป็น และยังไม่กำหนดว่าแจ้งเมื่อเหตุการณ์ใด
- **ลำดับ:** ทำเมื่อเรื่อง Must เสร็จแล้ว และตัดได้เมื่อเวลาไม่พอ [Q4]

## กลุ่ม 2: เจ้าหน้าที่ศูนย์ 1555 (P2)

### US2.1 ดูรายการและรายละเอียด Ticket (Must Have)

- **เรื่อง:** ในฐานะเจ้าหน้าที่ศูนย์ 1555 ฉันต้องการดูรายการ Ticket กรองตามสถานะ และเปิดดูรายละเอียด เพื่อให้ตามงานได้
- **ความต้องการที่เกี่ยวข้อง:** FR4.1, NFR2
- **เกณฑ์ผ่าน:**
  - **AC2.1.1** Given มี Ticket สถานะต่างกันหลายใบ When เจ้าหน้าที่กรองตามสถานะ "รับเรื่องแล้ว" Then แสดงเฉพาะ Ticket ที่มีสถานะนั้น
  - **AC2.1.2** Given เจ้าหน้าที่เลือก Ticket ใบหนึ่ง When เปิดรายละเอียด Then เห็นประเภทปัญหา สถานที่ ความเร่งด่วน ข้อความสรุป เวลาที่แจ้ง สถานะ และหน่วยงานรับผิดชอบ
  - **AC2.1.3** Given ยังไม่มี Ticket ในระบบ When เจ้าหน้าที่เปิดรายการ Then หน้าจอบอกว่ายังไม่มี Ticket
- **ลำดับ:** ต้องทำต่อจาก US1.2
- **คำถามค้าง:** ข้อความสำหรับรายการว่างเป็นการกำหนดตามหลักตรวจมุมเงื่อนไข ยังไม่ผ่านการยืนยัน [assumption]

### US2.2 เปลี่ยนสถานะ Ticket (Must Have)

- **เรื่อง:** ในฐานะเจ้าหน้าที่ศูนย์ 1555 ฉันต้องการเปลี่ยนสถานะ Ticket เอง เพื่อให้ประชาชนเห็นสถานะที่ถูกต้อง
- **ความต้องการที่เกี่ยวข้อง:** FR4.3, FR4.4
- **เกณฑ์ผ่าน:**
  - **AC2.2.1** Given Ticket สถานะ "รับเรื่องแล้ว" When เจ้าหน้าที่เปลี่ยนเป็น "กำลังดำเนินการ" Then Ticket แสดงสถานะ "กำลังดำเนินการ"
  - **AC2.2.2** Given Ticket สถานะ "กำลังดำเนินการ" When เจ้าหน้าที่เปลี่ยนเป็น "แก้ไขเสร็จ" Then ประชาชนที่กรอก Ticket ID เห็นสถานะ "แก้ไขเสร็จ"
- **ลำดับ:** ต้องทำต่อจาก US2.1
- **คำถามค้าง:** ยังไม่ได้กำหนดว่าย้อนสถานะกลับได้หรือไม่ [assumption]

### US2.3 เห็นสรุป 3 ข้อและข้อมูล Ticket เมื่อสายโอนเข้า (Could Have)

- **เรื่อง:** ในฐานะเจ้าหน้าที่ศูนย์ 1555 ฉันต้องการเห็นสรุป 3 ข้อและข้อมูล Ticket ทันทีที่สายโอนเข้า เพื่อช่วยประชาชนต่อได้เร็ว
- **ความต้องการที่เกี่ยวข้อง:** FR6.1, FR6.3
- **เกณฑ์ผ่าน:**
  - **AC2.3.1** Given สายถูกโอนเข้า Genesys Agent Workspace When Widget เปิดขึ้น Then ส่วนบนสุดแสดงสรุป 3 ข้อ และข้อมูล Ticket (ประเภทปัญหา สถานที่ ความเร่งด่วน หน่วยงานรับผิดชอบ)
- **ลำดับ:** ต้องทำต่อจาก US1.2 ตัดได้เมื่อเวลาไม่พอ ซึ่งต้องตัดฉากสาธิตหน้าจอเจ้าหน้าที่และตัวชี้วัด AHT ตามไปด้วย [scope-document.md]
- **คำถามค้าง:** เนื้อหาของ "สรุป 3 ข้อ" ว่าต้องมีอะไรบ้าง ยังไม่กำหนด

### US2.4 เปิดบทสนทนาสดเพื่ออ่านเพิ่ม (Could Have)

- **เรื่อง:** ในฐานะเจ้าหน้าที่ศูนย์ 1555 ฉันต้องการเปิดบทสนทนาสดภาษาไทยเมื่ออยากอ่านรายละเอียดเพิ่ม เพื่อไม่พลาดสิ่งที่ประชาชนพูด
- **ความต้องการที่เกี่ยวข้อง:** FR6.2
- **เกณฑ์ผ่าน:**
  - **AC2.4.1** Given Widget แสดงสรุปแล้ว When เจ้าหน้าที่เปิดส่วนบทสนทนาสด Then เห็นข้อความภาษาไทยของบทสนทนาของสายนั้น
- **ลำดับ:** ต้องทำต่อจาก US2.3
- **คำถามค้าง:** ค่าหน่วงเวลาที่ยอมรับได้ของบทสนทนาสดยังไม่ได้กำหนด (ใน Q1 ของ Requirements Analysis คุณเลือกเฉพาะเวลาตอบ 2 วินาที) และยังไม่ชัดว่าบทสนทนาสดแสดงชั่วคราวได้โดยไม่บันทึกลง Ticket (FR2.5) [assumption]

### US2.5 ส่ง Ticket ต่อให้สำนักงานเขต (Could Have)

- **เรื่อง:** ในฐานะเจ้าหน้าที่ศูนย์ 1555 ฉันต้องการกดส่ง Ticket ต่อให้สำนักงานเขต เพื่อให้หน่วยงานรับผิดชอบรับเรื่องไปดำเนินการ
- **ความต้องการที่เกี่ยวข้อง:** FR2.6
- **เกณฑ์ผ่าน:**
  - **AC2.5.1** Given Ticket มีเขตระบุแล้ว When เจ้าหน้าที่กดปุ่มส่งต่อ Then Ticket ถูกทำเครื่องหมายว่าส่งต่อให้สำนักงานเขตนั้น
- **ลำดับ:** ต้องทำต่อจาก US2.1
- **คำถามค้าง:** ไม่ได้กำหนดว่าการ "ส่งต่อ" ในต้นแบบทำอะไรจริง เพราะการเชื่อมระบบรับเรื่องของ กทม. อยู่นอกขอบเขต [assumption]

---

## กลุ่ม 3: เจ้าหน้าที่สำนักงานเขต (P3)

### US3.1 รับและติดตาม Ticket ที่ส่งต่อมา (Could Have)

- **เรื่อง:** ในฐานะเจ้าหน้าที่สำนักงานเขต ฉันต้องการเห็น Ticket ที่ส่งต่อมาให้เขตของฉันพร้อมข้อมูลครบ และติดตามสถานะได้ เพื่อดำเนินการได้ทันที
- **ความต้องการที่เกี่ยวข้อง:** FR2.4, FR4.1
- **เกณฑ์ผ่าน:**
  - **AC3.1.1** Given Ticket ถูกส่งต่อให้สำนักงานเขตหนึ่ง When เจ้าหน้าที่ของเขตนั้นเปิดรายการ Ticket Then เห็น Ticket นั้นพร้อมประเภทปัญหา สถานที่ ความเร่งด่วน และสถานะ
- **ลำดับ:** ต้องทำต่อจาก US2.5
- **คำถามค้าง:** ยังไม่ได้กำหนดว่าเจ้าหน้าที่สำนักงานเขตใช้หน้าจอเดียวกับเจ้าหน้าที่ศูนย์หรือหน้าจอแยก และเปลี่ยนสถานะได้หรือไม่ (FR4.4 ระบุเฉพาะ "เจ้าหน้าที่")

## Won't Have (เวอร์ชันแรก)

- ช่องทางข้อความรับเรื่อง (Web Chat / LINE), การ Fine-tune โมเดลใหม่, ฐานข้อมูลระเบียบครบ 50 เขต และการเชื่อมระบบรับเรื่องจริงของ กทม. [intent-statement.md]

## ความต้องการที่ไม่มีเรื่องราวโดยตรง

- FR8 และ FR6 ถูกครอบคลุมโดย US1.8, US2.3 ถึง US2.4
- NFR4 (TDD และ coverage 80%) และ NFR5 (รันบนเครื่องของทีม) เป็นข้อกำหนดของการสร้างและการรัน ไม่ใช่ผลลัพธ์ที่ผู้ใช้เห็น จึงส่งต่อไปขั้นตอนถัดไป

## Assumptions & Open Questions

- ผลที่ต้องการเมื่อถามกลับสถานที่ 1 ครั้งแล้วยังไม่ชัด (US1.3) ยังไม่กำหนด [assumption]
- ข้อความรายการ Ticket ว่าง (US2.1) และการย้อนสถานะ (US2.2) ยังไม่ผ่านการยืนยัน [assumption]
- หัวข้อของการถามข้อมูลระเบียบ กทม. (US1.6) ยังไม่กำหนด [assumption]
- วิธีที่ประชาชนได้ Ticket ID เมื่อ SMS ส่งไม่ถึง และช่องทางส่ง SMS (US1.4) ยังไม่กำหนด [assumption]
- การป้องกันการเดา Ticket ID (US1.5) ยังไม่ตัดสิน [assumption]
- เนื้อหาของสรุป 3 ข้อ (US2.3) และค่าหน่วงเวลาที่ยอมรับได้ของบทสนทนาสด (US2.4) ยังไม่ได้กำหนด [assumption]
- สิทธิของเจ้าหน้าที่สำนักงานเขต (US3.1) ยังไม่กำหนด [assumption]
- `scope-document.md` จัด SMS เป็น Could แต่ `requirements.md` จัดเป็น Must ต้องปรับเอกสารขอบเขตให้ตรงกัน [assumption]
